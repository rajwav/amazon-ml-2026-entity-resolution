## 1. The Fundamental ER Trade-Off

In large-scale Business Entity Resolution, candidate generation (blocking) is the first and most critical stage of the two-stage ER architecture:

```
[Target Universe: 10.3M records]
               │
               ▼
   ┌───────────────────────┐
   │  Stage 1: Blocking    │  <-- Focus: NEAR-PERFECT RECALL (>=99.9%)
   │  (Inverted Indexing)  │      Goal: Slash candidates by >50%-98%
   └───────────────────────┘
               │ Candidates (e.g. ~1,100 per query)
               ▼
   ┌───────────────────────┐
   │  Stage 2: Classifier  │  <-- Focus: ULTRA-HIGH PRECISION
   │  (LightGBM Ranker)    │      Optimized for Macro F0.5
   └───────────────────────┘
               │ Predicted Matches
               ▼
         Final Output
```

---

## 2. Mathematical Framing: Recall as Hard Constraint

Let $\mathcal{P}^* = \{(q, t) \mid q \in S1, t \in \text{Target}, \text{match}(q, t) = 1\}$ be the set of all true matching pairs in ground truth.  
Let $\mathcal{C}$ be the set of candidate pairs generated by the blocking stage.  
Let $\mathcal{M} \subseteq \mathcal{C}$ be the set of matching pairs predicted by the downstream classifier.

The end-to-end true-pair recall is strictly bounded by the blocker recall:
$$\text{Recall}_{\text{End-to-End}} = \frac{|\mathcal{M} \cap \mathcal{P}^*|}{|\mathcal{P}^*|} \le \frac{|\mathcal{C} \cap \mathcal{P}^*|}{|\mathcal{P}^*|} = \text{Recall}_{\text{Blocking}}$$

Any true pair missed during blocking ($\Delta \mathcal{P}^* = \mathcal{P}^* \setminus \mathcal{C}$) is **permanently eliminated**. No machine learning model, gradient-boosted tree, or deep neural network can predict a match that is not in the candidate set.

Therefore:
$$\mathbf{\text{Recall is the HARD CONSTRAINT: }} \text{Recall}_{\text{Blocking}} \ge 99.9\%$$

---

## 3. Candidate Volume as Optimization Objective

While recall is the hard constraint, candidate volume directly determines:
1. **Computational Feasibility:** Pairwise feature computation across $\mathcal{C}$. At $N = 1,732,544$ test queries, generating 3,295 candidates/query (Baseline G) yields **5.71 billion pairs**. Slashing candidates to 1,145/query (Champion v2) yields **1.98 billion pairs**—a reduction of **3.73 billion pairwise evaluations**!
2. **Class Imbalance in Downstream Classifier:** Lower candidate volume increases the positive-to-negative ratio from $1:1,000$ to $1:300$, drastically improving classifier convergence and precision calibration for Macro $F_{0.5}$.
3. **RAM Footprint:** Memory consumption during worker batch generation.

---

## 4. Formal Metric Definitions

For an evaluation dataset with $N$ queries ($S1$) and $T$ ground-truth pairs:

1. **True-Pair Recall:**
   $$\text{Recall} = \frac{\sum_{q \in S1} |\mathcal{C}(q) \cap \mathcal{P}^*(q)|}{|\mathcal{P}^*|} \times 100\%$$
2. **Average Candidates per Query:**
   $$\bar{C} = \frac{1}{N} \sum_{q \in S1} |\mathcal{C}(q)|$$
3. **Candidate Search Space Reduction Ratio:**
   $$\text{Reduction} = \left( 1 - \frac{\sum_{q \in S1} |\mathcal{C}(q)|}{N \times |\text{Targets}|} \right) \times 100\%$$
4. **Marginal Candidate Efficiency Ratio ($\Delta \text{Cands} / \Delta \text{TP}$):**
   $$\text{Efficiency} = \frac{|\mathcal{C}_{\text{new}}| - |\mathcal{C}_{\text{base}}|}{|\text{TP}_{\text{new}}| - |\text{TP}_{\text{base}}|}$$
   Measures the exact number of collateral non-matching candidates introduced to recover each additional true matching pair. Lower is better.
5. **Multi-Match Complete Recall:**
   $$\text{MultiMatch}_{\text{complete}} = \frac{|\{q \in S1 \mid |\mathcal{P}^*(q)| \ge 2 \text{ and } \mathcal{P}^*(q) \subseteq \mathcal{C}(q)\}|}{|\{q \in S1 \mid |\mathcal{P}^*(q)| \ge 2\}|} \times 100\%$$
   The percentage of multi-match queries where **100% of true targets** were recalled.
