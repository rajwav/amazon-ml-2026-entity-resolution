# Production Output Contract: Candidate Generation to Matching Interface

| Attribute | Specification |
|:---|:---|
| **Contract ID** | `CONTRACT-PHASE2-TO-PHASE3` |
| **Originating Component** | Candidate Generation Engine (Champion v2 Surgical) |
| **Consuming Component** | Feature Engineering & Pre-Ranking Pipeline (Phase 3) |
| **Status** | **LOCKED INTERFACE SPECIFICATION** |

---

## 1. Overview
This contract establishes the formal data interface between the candidate generation phase and the downstream feature extraction and classification phase.

---

## 2. File Format & Partitioning Strategy

- **Format**: Apache Parquet with Snappy or Zstandard compression (TSV format permitted for small development subsets).
- **Directory Layout**:
  ```text
  data/candidates/
  ├── country=IN/
  │   ├── part-00000.parquet
  │   ├── part-00001.parquet
  │   └── ...
  └── country=US/
      ├── part-00000.parquet
      ├── part-00001.parquet
      └── ...
  ```
- **Partitioning Key**: Hive-style `country=IN` and `country=US`.
- **Target File Size**: 100 MB to 250 MB per Parquet part file to enable parallel multi-threaded reading in PyArrow, Polars, or DuckDB.

---

## 3. Data Schema & Column Definitions

Each record in the candidate table represents a single candidate edge $(S1, \text{Target})$ generated by Champion v2:

| Column Name | Data Type | Nullable | Description / Semantics |
|:---|:---|:---|:---|
| `s1_id` | `VARCHAR(32)` | **NO** | Unique identifier of the query entity (e.g., `S1-438577211`). |
| `target_id` | `VARCHAR(32)` | **NO** | Unique identifier of the candidate target record (e.g., `S2-301716006`). |
| `country` | `VARCHAR(2)` | **NO** | ISO 2-letter country code (`IN` or `US`). Must match partition. |
| `channel_bitmask` | `INT32` | **NO** | Bitmask indicating which active channels generated this candidate pair. |
| `min_tier` | `INT8` | **NO** | Earliest hierarchical level that discovered the pair ($1 = \text{L1}$, $2 = \text{L2}$, $3 = \text{L3}$, $4 = \text{Tail}$). |

### Channel Bitmask Mapping
To assist downstream feature engineering with candidate provenance features, each candidate pair records a bitmask of matching channels:
- `Bit 0 (1)`: Level 1 Exact Normalized Name
- `Bit 1 (2)`: Level 1 Composite Keys (`tok_loc`, `tok_dig`, `pref_loc`, etc.)
- `Bit 2 (4)`: Level 2 Core Name / Significant Name Tokens
- `Bit 3 (8)`: Level 2 4-Character Name Prefix
- `Bit 4 (16)`: Level 2 Address Digits
- `Bit 5 (32)`: Level 3 Dynamic Top-2 Location Channel F
- `Bit 6 (64)`: Tail Channel T1 (2-Character Tokens)
- `Bit 7 (128)`: Tail Channel T2 (Domain & Social Handle Stem)
- `Bit 8 (256)`: Tail Channel T3 (Consonant Collapsed Name)
- `Bit 9 (512)`: Tail Channel T4 (Composite Enriched Digits + Loc)
- `Bit 10 (1024)`: Micro-Signal S2 (Consonant Trigram Prefix)
- `Bit 11 (2048)`: Micro-Signal S4 (US State + Street Digit)
- `Bit 12 (4096)`: Micro-Signal S5 (Alphanumeric Address Unit)

## 4. Invariants & Data Integrity Guarantees

1. **Uniqueness Guarantee**: For any given `s1_id`, all `target_id` values within the candidate set are strictly unique:
   $$\forall q, \quad |\{\text{target\_id} \mid s1\_id == q\}| == \text{count}(\text{candidates for } q)$$
2. **Intra-Country Isolation**:
   $$\forall \text{ edge}, \quad \text{country}(s1\_id) == \text{country}(target\_id)$$
3. **No Zero-Candidate Queries**: Every query $S1$ present in the input corpus must appear at least once in `s1_id` with non-empty candidates.
4. **Recall Guarantee**: True entity pairs present in the ground truth benchmark are guaranteed to exist within the candidate output with probability $\ge 99.98\%$.
